# go-zero Design Principles in Practice

## Purpose

This guide explains recurring design choices in go-zero projects. It distinguishes conventions generated by `goctl` from guarantees made by the runtime. Treat the selected go-zero source version and generated code as authoritative when details differ.

## Generated Boundaries

For REST services, `goctl` normally generates a flow like:

```text
route -> handler -> logic -> model or RPC client
```

- **Handler** parses the request, calls the logic method, and writes the response.
- **Logic** contains application behavior and orchestration.
- **Model** encapsulates datastore access.
- **ServiceContext** constructs and shares configuration, models, and clients.

This separation is a generated convention, not a runtime restriction. Preserve it because it keeps transport concerns out of business code and gives custom logic a stable place when code is regenerated.

```go
type ServiceContext struct {
    Config    config.Config
    UserModel model.UserModel
    UserRPC   userclient.User
}

func NewServiceContext(c config.Config) *ServiceContext {
    conn := sqlx.NewMysql(c.DataSource)
    return &ServiceContext{
        Config:    c,
        UserModel: model.NewUserModel(conn),
        UserRPC:   userclient.NewUser(zrpc.MustNewClient(c.UserRPC)),
    }
}
```

ServiceContext is a composition root. It should own long-lived dependencies, while request-scoped values remain in `context.Context` or method arguments.

## Code Generation as a Contract

`.api` and `.proto` files define transport contracts. `goctl` turns them into routing, types, clients, and implementation stubs.

Recommended workflow:

1. Change the source contract.
2. Regenerate with the repository's pinned `goctl` version.
3. Review generated diffs.
4. Implement or update logic code.
5. Run formatting, tests, and static analysis.

Avoid hand-editing generated files when regeneration will overwrite the change. If the repository intentionally customizes templates, version those templates and the generator version together.

## Configuration and Defaults

go-zero decodes configuration into Go structs and supports defaults through struct tags. The Go config type is the schema; a YAML key that is not represented there does not enable a feature merely because it looks plausible.

```go
type Config struct {
    rest.RestConf
    DataSource string
    UserRPC    zrpc.RpcClientConf
}
```

```yaml
Name: user-api
Host: 0.0.0.0
Port: 8888
Timeout: 3000
DataSource: ${MYSQL_DSN}
UserRPC:
  Endpoints:
    - user-rpc:8080
```

- Keep secrets out of committed configuration.
- Use explicit timeouts at service boundaries.
- Validate production configuration during startup.
- Check the config structs in the selected framework version before adding keys.

## Context Propagation

Generated logic structs carry the request context. Pass it to models, RPC clients, and outbound calls:

```go
func (l *GetUserLogic) GetUser(req *types.GetUserReq) (*types.GetUserResp, error) {
    user, err := l.svcCtx.UserModel.FindOne(l.ctx, req.ID)
    if err != nil {
        return nil, fmt.Errorf("find user %d: %w", req.ID, err)
    }
    return &types.GetUserResp{ID: user.Id, Name: user.Name}, nil
}
```

Context carries cancellation, deadlines, trace state, and request-scoped metadata. Do not store a request context in a singleton or replace it with `context.Background()` during a request unless the work intentionally outlives that request and has its own bounded lifecycle.

## Resilience at Boundaries

go-zero includes middleware and packages for timeouts, circuit breaking, load shedding, rate limiting, metrics, and tracing. These mechanisms reduce failure amplification, but they do not choose business policy.

For each outbound dependency, decide:

- the deadline budget;
- whether retries are safe and which errors are transient;
- the idempotency key for repeated operations;
- the fallback or degradation behavior;
- the metrics and logs needed to diagnose failure.

Do not add retries to non-idempotent writes without a deduplication strategy. Retrying at multiple layers can multiply traffic during an outage.

## Error Boundaries

Keep internal errors useful to operators and public errors safe for clients.

- Wrap infrastructure failures with operation context while preserving the cause with `%w`.
- Map domain errors to stable API or RPC error codes at the transport boundary.
- Do not expose SQL, topology, credentials, or stack traces in client responses.
- Log once at the layer that has enough context to act; avoid duplicating the same error at every layer.

## State and Scale

Stateless service processes are easier to replicate, but go-zero does not make application state external automatically.

- Put durable state in databases or durable queues.
- Treat in-memory caches, timers, and singleflight groups as replica-local optimizations.
- Use discovery or configured endpoints appropriate to the deployment environment.
- Design background workers for duplicate delivery and process restarts.
- Make graceful shutdown flush or stop owned resources within a bounded period.

## Review Heuristics

When reviewing a go-zero change, check:

- Does the contract change originate in `.api` or `.proto` where appropriate?
- Is generated transport code still thin?
- Are dependencies constructed once in ServiceContext?
- Does context reach every blocking call?
- Are timeouts and retries safe for the operation?
- Are model and queue operations idempotent where delivery can repeat?
- Are configuration keys backed by real config fields?
- Are public errors stable and free of sensitive detail?
- Can the service shut down without abandoning buffered work?
- Were examples and commands tested against the declared versions?

## When go-zero Fits

go-zero is a strong fit when a Go team benefits from generated API/RPC scaffolding, consistent service structure, and integrated production middleware. A smaller router or standard-library service may be simpler for a tiny application that does not need those conventions. Choose based on operational and team needs rather than assuming microservices are the default architecture.
